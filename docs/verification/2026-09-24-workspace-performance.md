# 516 页工作区压力样本（阶段 5，初次测量）

使用 `node --expose-gc --import tsx scripts/workspace-performance.ts`，SQLite、PDF Worker 与 Edge／Core HTTP 阅读界面均在本机运行；单笔修改时间在 Core 用例入口直接测量，不含 HTTP 传输。脚本生成临时 PDF 和工作区，结束后移除自己的临时目录；未读取或提交用户 PDF、数据库及派生画面。脚本在满载后连续提交 11 次单笔修改，再测量阅读页打开与滚动。

环境：Windows 11 内核版本 `10.0.26200`、Intel Core Ultra 7 155H、32 GiB RAM、Node 24。三次运行；生成样本为 516 页（仅首页含文字）、500 卡片、1000 关系、5000 笔迹对象／250000 点。该样本用于测量实体数量上限，不代表 516 页真实复杂书籍的解析成本。

| 测量 | 优化前 | 去除重复深度解析后 |
| --- | ---: | ---: |
| PDF 解析 | 1.54–1.63 s | 1.60–1.64 s |
| 写入满载工作区 | 176–231 ms | 193–237 ms |
| 读取完整工作区 | 221–245 ms | 138–158 ms |
| 满载后首次修改一笔的 Core 命令 | 467–530 ms | 348–378 ms |
| 后续 10 次单笔修改 P50 / P95 | 490–500 / 571–709 ms | 310–356 / 342–388 ms |
| 打开阅读页并呈现 500 卡片 | 1.14–1.21 s | 0.78–0.86 s |
| 滚动时帧间隔 P95 / P99 | 16.8 / 17–33.4 ms | 16.8 / 33.3–50.1 ms |
| 页面打开阶段最长主线程任务 | 164 ms 左右 | 158–168 ms |

Core 读回的工作区已由存储库校验，之前 `Workspaces.get` 再次深度解析会复制所有笔迹点；保存命令同样在领域层解析后又被存储库解析。去除这两处重复复制，保留未经过领域验证时的存储入口校验。满载单次命令约 0.35 s，连续 10 次 P95 约 0.34–0.39 s，仍是后续优化重点。

回归测试对存储库的原始写入和被篡改的数据库行分别断言拒绝，防止性能路径绕开书籍数据的运行时校验；本地 `pnpm typecheck` 及全量 `pnpm test`（31 文件／49 项）通过。实际 Windows runner 仍须对本次代码复核。

Edge JS heap 约 46–48 MiB；滚动采样通常无 ≥50 ms 长任务，某次有一个 55–59 ms 任务。默认 Node 堆配置下 Core RSS 在 11 次命令后约 1.0–1.1 GiB，强制 GC 后 V8 已用堆仅约 108–111 MiB。用 `--max-old-space-size=512` 的诊断运行将 RSS 限制在约 553 MiB，命令 P95 约 388 ms；这提示 V8 堆扩张／分配压力，但**没有**据此更改产品 Core 的堆上限。仍需持续编辑和真实 PDF 的资源趋势验收，不能以合成样本宣称内存问题已解决。

未覆盖：真实 516 页书籍的文字／图片复杂度、Windows 100%／200% 显示缩放、浅深主题截图、连续绘画时帧耗、长时间编辑后的内存趋势、普通用户安装环境。阶段 5 保持进行中。
