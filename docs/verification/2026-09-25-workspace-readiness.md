# PDF 渲染与工作区就绪边界

状态：`3118cd7` 的本机与 Windows CI 均通过；早先两次首步超时的唯一根因尚未被故障注入测试证明。

`b64b548` 的 Windows CI 36132679411 在“Cross-page ink and eraser acceptance”第一笔后等待 5 秒，Core 工作区仍没有对象。同一分支前两轮 CI 此步骤通过；此前 `05a4de6` 曾在文字对象的第一步出现相似超时。因此不能只把一次失败归为保存慢。代码检查发现 PDF 页的 `data-render-ready` 与 `WorkspaceEditingSession.load()` 是独立条件：前者可能先完成，而 `BookWorkspace.startInk()` 在 `state.value` 缺失时直接返回，手势没有可见结果。

修复使工作区未就绪的绘画／编辑入口提示用户，并且画笔不捕获未被接受的指针；阅读容器暴露就绪状态供验收等待。画笔和对象的验收都先等待 PDF 渲染及工作区就绪，再验证保存结果；首次画笔保存失败时输出工作区版本、错误提示、命令响应和页面异常，以便区分加载、保存和渲染问题。此改动不改变已完成的笔迹或 PDF 原文。

本机新构建的跨页画笔、对象编辑、区域摘录、材料选择、工作区滚轮与导航、PDF 区域问答烟测均通过。当前证据证明等待条件与现有操作相容，但没有人为注入 Core 延迟，因此仍不能断言曾经的两次超时只有这一个根因。

[Windows CI 36134178488](https://github.com/SoloEdge-ai/AIReader/actions/runs/36134178488) 全绿：先前失败的跨页画笔首笔验收、画布对象、打包版笔迹／对象、关闭保存、安装更新卸载和校验和均通过。该结果证实修复在本次 Windows runner 上可用，不等于已完成 Windows 11 实机全量验收。
